LMI maintains a minimum fleet of 3 instances at all times. If your workload has long idle periods, the always-on cost may outweigh the per-request savings.

## Quick reference

| Workload | Use LMI? | Why |
| --- | --- | --- |
| Steady, high-concurrency (>50 req/s sustained) | Yes | Multi-concurrency maximizes vCPU use |
| CPU or memory-intensive (>1 GB, long-duration) | Yes | Larger instance types and dedicated compute |
| Predictable, latency-sensitive traffic | Yes | Pre-warmed environments, no cold starts |
| Long-running jobs (>15 min, async or batch) | Yes | Up to a 90-minute timeout |
| Cost-sensitive, steady-state load | Yes | EC2 pricing with Savings Plans and RIs |
| Bursty or infrequent invocations | No | Standard Lambda scales to zero |
| Low-volume event-driven (S3, SQS) | No | Per-request pricing is cheaper |
| Need OS or agent access (e.g., CrowdStrike) | Evaluate | Managed instances: no SSH or agents |

Primary criteria from the [AWS documentation](https://docs.aws.amazon.com/lambda/latest/dg/lambda-managed-instances.html) :

- **High-volume predictable workloads** with steady-state traffic (LMI scales to handle traffic doubling within 5 minutes)
- **Performance-critical applications** needing recent-generation CPUs (such as Graviton4), configurable memory-CPU ratios, or high network throughput
- **Regulatory requirements** needing granular VPC and instance placement control
- **Cost optimization** through EC2 Savings Plans and Reserved Instances

For a full breakdown, see [How Lambda Managed Instances differs from the Lambda (default) compute type](https://docs.aws.amazon.com/lambda/latest/dg/lambda-managed-instances.html#lambda-managed-instances-comparison) .

Lambda Managed Instances supports a maximum function timeout of **90 minutes** (5,400 seconds) for **asynchronous** and **event source mapping** invocations, compared to 15 minutes for standard Lambda. That 6x increase removes a long-standing reason teams had to re-architect data-intensive jobs off Lambda: media transcoding, ETL and batch processing, financial modeling such as Monte Carlo simulations, AI inference, and large file transfers.

A few boundaries to keep in mind:

- The longer timeout applies to **asynchronous** and **event source mapping** invocations. **Synchronous** invocations keep the 15-minute maximum.
- The initialization (Init) phase is still capped at 15 minutes.
- You set it with a single configuration value and no code change: `Timeout: 5400` in CloudFormation or SAM, or `--timeout 5400` with the AWS CLI.
- There is no additional charge, standard LMI pricing applies, and it is available in every Region where LMI is available.

For jobs where restarting from scratch is expensive, pair the longer timeout with [Lambda durable functions](https://docs.aws.amazon.com/lambda/latest/dg/durable-functions.html) , which checkpoint progress and resume after a failure. A multi-step durable execution invoked asynchronously can run for up to a year.

Because functions can run much longer, plan for connections and credentials that might expire mid-run: keep downstream idle timeouts above your function duration, send keep-alive packets through a NAT gateway (350-second idle limit), and refresh temporary credentials that would otherwise expire before the job finishes.

The workshop does not deploy a long-running function, but the capacity provider and function model you build next is exactly what supports the 90-minute timeout, you set the timeout value on the function.

If you are already using [Lambda Provisioned Concurrency](https://docs.aws.amazon.com/lambda/latest/dg/provisioned-concurrency.html) to eliminate cold starts, LMI may be a better fit when:

- You need more than 10 GB memory per function
- You want EC2 pricing models (Savings Plans, Reserved Instances)
- Your workload benefits from multi-concurrency (I/O-heavy)
- You need specific instance types (Graviton, compute-optimized)
