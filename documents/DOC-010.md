When you roll LMI out into a regulated environment, security scanners and audit tools will find your managed EC2 instances and flag them against the same policies they apply to normal EC2 workloads. Some of those findings are automatically compliant. Some require a documented exception. A few genuinely need action on your part.

In this step you will learn:

1. IMDSv2 is enforced by default on all managed instances (no configuration needed)
2. How to triage common compliance scanner findings, which to fix and which to document as exceptions
3. What you cannot change on managed instances (agents, AMI, IMDS settings)
4. How to restrict egress traffic for production security groups
5. How to audit all capacity provider operations via CloudTrail
6. Enterprise governance patterns using SCPs and IAM naming conventions

## IMDSv2 is enforced by default

The Instance Metadata Service (IMDS) provides instance-level information to code running on the instance. IMDSv1 uses a request-response model that is vulnerable to SSRF attacks; IMDSv2 uses session tokens and is the required standard for most compliance frameworks.

LMI enforces IMDSv2 on every managed instance. You do not need to configure it, and you cannot roll back to IMDSv1.

Verify on one of your existing instances:

```bash
INSTANCE_ID=$(aws ec2 describe-instances \
  --include-managed-resources \
  --filters "Name=tag:aws:lambda:capacity-provider,Values=*lmi-workshop-capacity-provider" \
            "Name=instance-state-name,Values=running" \
  --query "Reservations[0].Instances[0].InstanceId" \
  --output text)

aws ec2 describe-instances \
  --instance-ids $INSTANCE_ID \
  --query "Reservations[0].Instances[0].MetadataOptions" \
  --output table
```

The output shows the metadata options in force on the instance:

```
------------------------------------------------------------------------------------------------------------------
|                                                DescribeInstances                                               |
+--------------+-------------------+--------------------------+-------------+------------------------+-----------+
| HttpEndpoint | HttpProtocolIpv6  | HttpPutResponseHopLimit  | HttpTokens  | InstanceMetadataTags   |   State   |
+--------------+-------------------+--------------------------+-------------+------------------------+-----------+
|  enabled     |  disabled         |  2                       |  required   |  disabled              |  applied  |
+--------------+-------------------+--------------------------+-------------+------------------------+-----------+
```

`HttpTokens: required` is the definitive signal that IMDSv2 is enforced and IMDSv1 is disabled. The `HttpPutResponseHopLimit: 2` is required because LMI functions run inside containers on the host. A hop limit of 1 would block container access to the instance metadata service. This value is set by the service and is correct.

If a scanner reports "EC2 Instances must have IMDSv1 Disabled" against your managed instances, you can close the finding immediately. The value is already `required`.

## How to read common scanner findings

Below is a triage guide for the compliance findings your team is most likely to see against LMI-owned instances:

| Finding | Status on LMI | Recommended action |
| --- | --- | --- |
| EC2 Instances must have IMDSv1 disabled | Compliant | No action needed. `HttpTokens: required` is set. |
| EC2 Instance does not have host-monitoring agent | Not applicable | Managed instances cannot host third-party agents. Document as accepted risk with security team. |
| EC2 Instance not using approved AMI | Not applicable | Lambda chooses and patches the AMI. Document as an AWS-managed control. |
| EC2 Instance missing required tags | Actionable | Enable `PropagateTags` on the capacity provider (Module 3, Tag Propagation). |
| EBS volumes must be encrypted with a CMK | Actionable | Attach a customer-managed KMS key on the capacity provider (previous step). |
| EC2 Instance not in approved VPC | Actionable | Attach the capacity provider to an approved VPC and subnets. |
| Security group allows unrestricted egress | Evaluate | Depends on your egress policy. See below. |

## Findings you cannot fix

These findings will show up against LMI instances and there is nothing operational you can do to close them, because the underlying control is owned by AWS:

- Cannot install monitoring agents (CrowdStrike, Qualys, host-based IDS): Lambda manages the OS.
- Cannot modify the AMI: Lambda selects and patches it.
- Cannot change IMDS settings after launch: they are enforced at launch time by the service.
- Cannot attach IAM instance profiles directly: the capacity provider's operator role handles instance-level permissions.

The workflow for these is standardized:

1. **Document** in your change record that the instances are LMI-managed, not standard EC2.
2. **Request a policy exception** from your security team, citing the AWS-managed nature of the control.
3. **Reference** the [Lambda Managed Instances security documentation](https://docs.aws.amazon.com/lambda/latest/dg/lambda-managed-instances-security.html) as your evidence source.

## Restricting egress traffic

The workshop security group allows all outbound traffic. For production, most compliance frameworks want you to explicitly enumerate destinations.

See what the workshop security group looks like today:

```bash
aws ec2 describe-security-groups \
  --group-ids $SECURITY_GROUP_ID \
  --query "SecurityGroups[0].IpPermissionsEgress" \
  --output table
```

At a minimum, LMI functions need HTTPS egress to reach the AWS APIs they call: CloudWatch Logs (mandatory, or your functions can't ship logs), X-Ray if enabled, and any AWS service the function code calls directly. Beyond that, add rules for the external endpoints your function depends on.

| Destination | Port | Purpose |
| --- | --- | --- |
| NAT gateway or internet route | 443 | CloudWatch Logs, X-Ray, AWS API calls |
| VPC interface endpoints (if configured) | 443 | Private connectivity to AWS services |
| Application dependencies (databases, external APIs) | Varies | Whatever the function calls |

Over-restrict egress and your functions fail silently: log delivery to CloudWatch stops working. Always leave port 443 (HTTPS) open to your NAT gateway or the relevant VPC endpoints.

## Audit trail

Every capacity provider operation is logged in AWS CloudTrail. This includes `CreateCapacityProvider`, `UpdateCapacityProvider`, `DeleteCapacityProvider`, and `PutFunctionScalingConfig`, along with the identity that invoked each call. Auditors will ask for this evidence, and it's already there.

Query the most recent capacity provider creations to see the shape of the events:

```bash
aws cloudtrail lookup-events \
  --lookup-attributes AttributeKey=EventName,AttributeValue=CreateCapacityProvider \
  --max-results 5 \
  --query "Events[*].[EventTime,Username,EventName]" \
  --output table
```

For a full audit, filter CloudTrail on the `lambda.amazonaws.com` event source and the specific event names above.

## Enterprise governance patterns

When rolling LMI out across an organization, use these mechanisms to enforce standards:

| Control | Mechanism | Scope |
| --- | --- | --- |
| Require tags on capacity provider creation | SCP with `aws:RequestTag` condition | Organization-wide |
| Restrict who can create providers | SCP with `aws:PrincipalTag` condition | Organization-wide |
| Control function-to-provider attachment | IAM `lambda:PassCapacityProvider` | Per role |
| Force customer-managed encryption | SCP denying creation without `KmsKeyArn` | Organization-wide |
| Audit every operation | CloudTrail (automatic) | Account-wide |

Example SCP that denies capacity provider creation without required tags:

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "RequireTagsOnCapacityProviders",
      "Effect": "Deny",
      "Action": "lambda:CreateCapacityProvider",
      "Resource": "*",
      "Condition": {
        "Null": {
          "aws:RequestTag/Environment": "true",
          "aws:RequestTag/CostCenter": "true"
        }
      }
    }
  ]
}
```

SCPs apply at the AWS Organizations level and cannot be tested in this workshop account. These examples illustrate patterns you would apply in your own organization.

Use a naming convention for capacity providers (e.g. `production-payments-api`, `staging-data-science-batch`) combined with IAM resource ARN patterns to enforce placement. Replace `123456789012` with your account ID:

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "AllowPaymentsTeamProductionOnly",
      "Effect": "Allow",
      "Action": "lambda:PassCapacityProvider",
      "Resource": "arn:aws:lambda:*:123456789012:capacity-provider:production-payments-*"
    }
  ]
}
```

This role can only attach functions to `production-payments-*` capacity providers, preventing accidental cross-team placement.
