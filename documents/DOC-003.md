Now that your capacity provider is active, you will deploy a Lambda function configured to run on Lambda Managed Instances.

In this step you will:

1. Write a simple CPU-bound Python function (prime number calculator)
2. Package it as a zip and create the Lambda function attached to your capacity provider
3. Publish a version, which triggers Lambda to launch EC2 instances (2-5 minute wait)
4. Invoke the function and confirm zero cold starts
5. Verify the managed EC2 instances are running across Availability Zones

The key difference from standard Lambda: publishing a version **provisions real EC2 instances** in your VPC. Until you publish, no compute runs. After publishing, your function runs on always-warm instances with no cold start penalty.

## The function code

You will deploy a simple CPU-bound Python function that calculates prime numbers. This workload is intentionally compute-intensive to demonstrate LMI's multi-vCPU execution environments in later modules.

```python
import json
import time

def lambda_handler(event, context):
    """CPU-intensive function that finds prime numbers."""
    count = event.get("count", 1000)
    start = time.time()

    primes = []
    for num in range(2, count):
        is_prime = True
        for i in range(2, int(num**0.5) + 1):
            if num % i == 0:
                is_prime = False
                break
        if is_prime:
            primes.append(num)

    duration = time.time() - start

    return {
        "statusCode": 200,
        "body": json.dumps({
            "message": "Hello from Lambda Managed Instances!",
            "primes_found": len(primes),
            "duration_seconds": round(duration, 3),
            "request_id": context.aws_request_id
        })
    }
```

This function finds all prime numbers up to a configurable limit and returns the count and execution time.

## Create and deploy the function

Follow either the **Console** tab or the **AWS CLI** tab, not both.

Save the function code to a file and package it as a zip:

```bash
mkdir -p ./function

cat > ./function/lambda_function.py << 'EOF'
import json
import time

def lambda_handler(event, context):
    """CPU-intensive function that finds prime numbers."""
    count = event.get("count", 1000)
    start = time.time()

    primes = []
    for num in range(2, count):
        is_prime = True
        for i in range(2, int(num**0.5) + 1):
            if num % i == 0:
                is_prime = False
                break
        if is_prime:
            primes.append(num)

    duration = time.time() - start

    return {
        "statusCode": 200,
        "body": json.dumps({
            "message": "Hello from Lambda Managed Instances!",
            "primes_found": len(primes),
            "duration_seconds": round(duration, 3),
            "request_id": context.aws_request_id
        })
    }
EOF

cd ./function && zip function.zip lambda_function.py && cd ..
```

Later modules reuse `./function/function.zip`, so keep it in place.

Now create the function with the capacity provider configuration:

```bash
export CP_ARN=$(aws lambda get-capacity-provider \
  --capacity-provider-name lmi-workshop-capacity-provider \
  --query "CapacityProvider.CapacityProviderArn" \
  --output text)

echo "Capacity Provider ARN: $CP_ARN"
echo "Execution Role: $EXECUTION_ROLE_ARN"
```

Both values should be populated. If `EXECUTION_ROLE_ARN` is empty, re-run the environment variable exports from [Getting Started](https://catalog.us-east-1.prod.workshops.aws/event/dashboard/en-US/workshop/getting-started).

Create the function with the capacity provider configuration:

```bash
aws lambda create-function \
  --function-name lmi-workshop-function \
  --runtime python3.14 \
  --handler lambda_function.lambda_handler \
  --zip-file fileb://function/function.zip \
  --role "$EXECUTION_ROLE_ARN" \
  --memory-size 2048 \
  --capacity-provider-config "LambdaManagedInstancesCapacityProviderConfig={CapacityProviderArn=$CP_ARN,ExecutionEnvironmentMemoryGiBPerVCpu=2.0}"
```

You should see output confirming the function was created with the capacity provider attached.


Note the `PerExecutionEnvironmentMaxConcurrency: 16`. For Python the default is 16 concurrent requests **per vCPU**. Because this environment is sized at 1 vCPU, that works out to 16 per environment here; a 2-vCPU environment would handle 32.

Verify the function was created:

```bash
aws lambda get-function \
  --function-name lmi-workshop-function \
  --query "Configuration.[FunctionName,State]" \
  --output text
```

You should see `lmi-workshop-function   ActiveNonInvocable`. The `ActiveNonInvocable` state means the function exists but cannot be invoked yet. It needs a published version first.

Now publish a version to trigger instance provisioning:

```bash
export LMI_VERSION=$(aws lambda publish-version \
  --function-name lmi-workshop-function \
  --description "Initial LMI deployment" \
  --query "Version" \
  --output text)

echo "Published version: $LMI_VERSION"
```

The command extracts just the version number and prints it:

```
Published version: 1
```

Publishing triggers Lambda to provision EC2 instances and initialize execution environments. This takes 2-5 minutes.

Wait for the function version to become active:

```bash
echo "Waiting for lmi-workshop-function:$LMI_VERSION to become Active..."
while [ "$(aws lambda get-function --function-name lmi-workshop-function:$LMI_VERSION --query 'Configuration.State' --output text)" != "Active" ]; do
  echo "  Still provisioning... ($(date +%H:%M:%S))"
  sleep 15
done
echo "Function is Active!"
```

This polling loop takes 2 to 5 minutes while Lambda provisions EC2 instances. You will see "Still provisioning..." messages every 15 seconds until the function is ready.

Verify the state:

```bash
aws lambda get-function \
  --function-name lmi-workshop-function:$LMI_VERSION \
  --query "Configuration.State" \
  --output text
```

The output should show:

```
Active
```

**Key configuration parameters:**

| Parameter | Value | Why |
| --- | --- | --- |
| `--runtime python3.14` | Python 3.14 | LMI supports Python, Java, Node.js,.NET, and Rust (via `provided.al2023`). Python uses process-based multi-concurrency. |
| `--memory-size 2048` | 2048 MB | Determines the execution environment size. Combined with the ratio, this gives you 1 vCPU per environment. |
| `ExecutionEnvironmentMemoryGiBPerVCpu=2.0` | 2:1 ratio | Tells Lambda to select compute-optimized instances (2 GB memory per 1 vCPU). Lambda picks the actual instance type (e.g., m7a.xlarge) from available capacity in your region. |
| `PerExecutionEnvironmentMaxConcurrency=16` | 16 per vCPU (default) | Python defaults to 16 concurrent requests per vCPU. This 1-vCPU environment handles 16; a 2-vCPU environment would handle 32. |
| `--timeout` (left at the 3s default here) | 3 s | On LMI, asynchronous and event source mapping invocations support up to a 90-minute timeout (`--timeout 5400`); synchronous invocations keep the 15-minute maximum. |

You control the ratio, Lambda controls the instance type. The instance you see in your account (e.g., m7a.xlarge) may differ from other participants. What matters is the vCPU count and memory per vCPU, not the specific instance family.

Invoke the function to confirm it works with no cold start:

```bash
aws lambda invoke \
  --function-name lmi-workshop-function:$LMI_VERSION \
  --payload '{"count": 5000}' \
  --cli-binary-format raw-in-base64-out \
  response.json

cat response.json | python3 -m json.tool
```

You should see:

```json
{
    "StatusCode": 200,
    "ExecutedVersion": "1"
}
{
    "statusCode": 200,
    "body": "{\"message\": \"Hello from Lambda Managed Instances!\", \"primes_found\": 669, \"duration_seconds\": 0.002, \"request_id\": \"abc123-def456\"}"
}
```

The function executed in 2 ms with no cold start since the execution environment was pre-warmed during publishing.

Unlike standard Lambda (where execution environments are invisible to you), LMI runs your function on real EC2 instances that you can see. These instances are managed by Lambda (you cannot SSH into them or modify them), but you can verify they exist. Lambda launched a minimum of 3 instances across Availability Zones for high availability when you published the version.

The `--include-managed-resources` flag (requires AWS CLI v2) makes these Lambda-managed instances visible in EC2 describe commands:

```bash
aws ec2 describe-instances \
  --include-managed-resources \
  --filters "Name=tag:aws:lambda:capacity-provider,Values=*lmi-workshop-capacity-provider" \
            "Name=instance-state-name,Values=running" \
  --query "Reservations[*].Instances[*].[InstanceId,InstanceType,State.Name,Placement.AvailabilityZone]" \
  --output table
```

You should see 3 running instances spread across Availability Zones. This confirms Lambda provisioned real EC2 compute for your function:

```
-------------------------------------------------------------------
|                        DescribeInstances                        |
+----------------------+-------------+----------+-----------------+
|  i-0abc123def456789  |  m7a.xlarge |  running |  us-east-1a     |
|  i-0def456ghi789012  |  m7a.xlarge |  running |  us-east-1b     |
|  i-0ghi789jkl012345  |  m7a.xlarge |  running |  us-east-1c     |

```

The 3 instances across AZs provide high availability. Lambda chose the instance type (e.g., `m7a.xlarge`) based on your memory-to-vCPU ratio setting. Your instance type may differ.

## What just happened?

When you published the function version, Lambda:

1. Launched **3 EC2 instances** (minimum for AZ resiliency) in your private subnets
2. Started **3 execution environments** on those instances
3. Marked the function version as **Active** once environments were ready

This is the first function on this capacity provider, so Lambda provisioned new instances. For subsequent functions attached to the same provider, Lambda may reuse existing instances if they have available capacity, and the version becomes Active faster.

Your function is now running on dedicated EC2 instances with no cold starts. Execution environments are pre-warmed and ready to handle requests.

Unlike standard Lambda, LMI functions must be published before they can be invoked. The `$LATEST` version does not run on managed instances. Publishing is what triggers Lambda to provision the EC2 instances and create execution environments. Without publishing, no compute is allocated.

You cannot perform standard EC2 operations (terminate, stop, SSH) on managed instances. To remove them, delete the capacity provider. Lambda will terminate the instances automatically.

## Instance lifecycle

Understanding when instances start and stop helps you manage costs:

| Action | What happens to instances |
| --- | --- |
| Create capacity provider | Nothing (no instances launched) |
| Publish first function version | Lambda launches 3 instances (minimum for AZ resiliency) |
| Publish additional functions on same CP | Lambda reuses existing instances if capacity allows |
| Delete the capacity provider | Lambda terminates all instances |

To stop incurring EC2 costs, delete the capacity provider. You must first delete all functions attached to it. The [Cleanup](https://catalog.us-east-1.prod.workshops.aws/event/dashboard/en-US/workshop/cleanup) page walks through this in the correct order.

| Issue | Cause | Fix |
| --- | --- | --- |
| State stays "Pending" for >5 minutes | Instance provisioning delay | Check capacity provider state is "Active" first. If so, wait. First publish can take up to 5 minutes. |
| "InvalidParameterValueException" | Capacity provider ARN wrong | Verify the CP\_ARN variable is set. Run `echo $CP_ARN`. |
| Function created but can't invoke | Invoking `$LATEST` instead of `:1` | Always invoke with the version qualifier: `lmi-workshop-function:$LMI_VERSION` |
| "TooManyRequestsException" on invoke | Environments not ready yet | Wait for `function-active-v2` to complete before invoking. |

Your first LMI function is deployed, invoked, and running on managed EC2 instances. In the next step, you will deploy the same function on standard Lambda for comparison.
