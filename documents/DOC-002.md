In this step you will:

1. Create a capacity provider that tells Lambda **where** to launch instances (which VPC and subnets) and **how much** compute to allow (MaxVCpuCount)
2. Verify it transitions from `Pending` to `Active` (typically 30-60 seconds)
3. Understand how Lambda selects instance types based on your configuration

After this step, you will have the infrastructure in place but no instances running yet. Instances are launched only when you publish a function version in the next step.

## Understanding the components

Before creating the capacity provider, review what has been pre-provisioned for you:

- **VPC with private subnets**: 3 subnets across Availability Zones with NAT gateway for outbound connectivity
- **Security group**: egress-only, allowing your functions to reach AWS services
- **Operator role**: IAM role with `AWSLambdaManagedEC2ResourceOperator` policy that grants Lambda permission to launch and manage EC2 instances

Unlike standard Lambda (which runs in AWS-managed networking), LMI launches real EC2 instances that need to be placed somewhere in your network:

- **VPC**: provides network isolation. Your managed instances run inside your VPC, giving you control over routing and connectivity.
- **Private subnets (multiple AZs)**: Lambda distributes instances across Availability Zones for high availability. Private subnets ensure instances have no public IP. They reach the internet (for CloudWatch Logs, X-Ray) via the NAT gateway.
- **Security group**: controls network traffic to/from managed instances. Egress-only means your functions can call external services but nothing can connect inbound to the instances.
- **Operator role**: Lambda needs permission to call EC2 APIs (RunInstances, TerminateInstances, etc.) on your behalf. This role is assumed by the Lambda service, not by your function code.

For more details, see [Networking for Lambda Managed Instances](https://docs.aws.amazon.com/lambda/latest/dg/lambda-managed-instances-networking.html) .

## Create the capacity provider

Choose **one** tab below. Follow either the Console path or the AWS CLI path, not both. Both achieve the same result. If you choose the AWS CLI path, make sure you have completed the [Getting Started](https://catalog.us-east-1.prod.workshops.aws/event/dashboard/en-US/workshop/getting-started) and your environment variables (`$VPC_ID`, `$SUBNET_IDS`, `$SECURITY_GROUP_ID`, `$OPERATOR_ROLE_ARN`) are set. If not, run those prerequisites first.

Confirm the pre-provisioned resources are available (CLI users):

```bash
echo "VPC: $VPC_ID"
echo "Subnets: $SUBNET_IDS"
echo "Security Group: $SECURITY_GROUP_ID"
echo "Operator Role: $OPERATOR_ROLE_ARN"
```

All four values should be populated. If any are empty, return to [Getting Started](https://catalog.us-east-1.prod.workshops.aws/event/dashboard/en-US/workshop/getting-started) and re-run the environment variable exports.

Run the following commands in the IDE terminal you opened during [Getting Started](https://catalog.us-east-1.prod.workshops.aws/event/dashboard/en-US/workshop/getting-started). If you closed the terminal, open a new one from the menu: **Terminal > New Terminal**.

Create the capacity provider using the environment variables set during Getting Started:

```bash
aws lambda create-capacity-provider \
  --capacity-provider-name lmi-workshop-capacity-provider \
  --vpc-config "SubnetIds=[$SUBNET_IDS],SecurityGroupIds=[$SECURITY_GROUP_ID]" \
  --permissions-config "CapacityProviderOperatorRoleArn=$OPERATOR_ROLE_ARN" \
  --instance-requirements "Architectures=[x86_64]" \
  --capacity-provider-scaling-config "MaxVCpuCount=30"
```

You should see output confirming the capacity provider was created with State: `Pending`. The JSON response includes the capacity provider ARN, VPC configuration, and scaling config. Your subnet IDs, security group, and role ARN will differ.

## What just happened?

You created a capacity provider with the following configuration:

| Setting | Value | Why |
| --- | --- | --- |
| Subnets | 3 private subnets across AZs | High availability, Lambda distributes instances across AZs |
| Security group | Egress-only | Functions can reach AWS services but accept no inbound traffic |
| Architecture | x86\_64 | Default architecture. ARM (Graviton) is also supported |
| Instance types | Default (Lambda chooses) | Recommended for availability. Restricting types may reduce capacity |
| Max vCPUs | 30 | Caps total compute to control costs during the workshop |

## How Lambda selects instance types

You do **not** directly choose instance types like you would with EC2. By default, Lambda chooses optimal instance types for your workload based on availability in your region. You have two levels of control:

**1\. Memory-to-vCPU ratio (set on the function):** Determines how each execution environment is sized. Lambda selects instances that can efficiently fit environments with your chosen ratio.

| Ratio | Memory per vCPU | Best for |
| --- | --- | --- |
| 2:1 | 2 GB | CPU-heavy work (encoding, calculation) |
| 4:1 | 4 GB | Balanced workloads (APIs, web apps) |
| 8:1 | 8 GB | Memory-heavy work (caching, ML inference) |

**2\. Instance type filters (optional, set on the capacity provider):** You can restrict which instance types Lambda is allowed to use via `AllowedInstanceTypes` or `ExcludedInstanceTypes`. We did not set these, so Lambda has full flexibility.

From the [AWS documentation](https://docs.aws.amazon.com/lambda/latest/dg/lambda-managed-instances-capacity-providers.html) : "By default, Lambda chooses optimal instance types for your workload. We recommend letting Lambda Managed Instances choose instance types for you, as restricting the number of possible instance types may result in lower availability."

The instance type you see in your account (e.g., `m7a.xlarge`) may differ from other participants or change between deployments. What matters is the vCPU count and memory per environment, not the specific instance family.

| Issue | Cause | Fix |
| --- | --- | --- |
| State stays "Pending" | Rare, usually transitions in seconds | Wait 30 seconds and refresh. If still pending, check CloudTrail for errors. |
| "Access Denied" error | Operator role missing permissions | Verify `LMIWorkshopOperatorRole` has the `AWSLambdaManagedEC2ResourceOperator` managed policy attached. |
| "SubnetNotFound" error | Wrong subnet IDs | Re-run the environment variable export for `$SUBNET_IDS` and verify the values. |
| zsh: no matches found | Brackets not quoted | Wrap the `--vpc-config` and `--instance-requirements` values in double quotes. |
