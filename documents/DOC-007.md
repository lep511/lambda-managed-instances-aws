Grouping decisions determine both your isolation posture and your bill. Every capacity provider carries a minimum floor of three EC2 instances, so each additional provider you introduce raises your baseline cost. Isolation you don't actually need is money you shouldn't spend; isolation you do need is not optional.

Three grouping patterns cover most workloads.

## Strategy 1: One shared provider

Every function attaches to a single capacity provider.

![One Shared Provider](https://static.us-east-1.prod.workshops.aws/a9696d28-e07e-41f2-b1ac-ae40faf46ec0/static/images/module-4/architecture-1-shared-provider.png?Key-Pair-Id=K36Q2WVO3JP7QD&Policy=eyJTdGF0ZW1lbnQiOlt7IlJlc291cmNlIjoiaHR0cHM6Ly9zdGF0aWMudXMtZWFzdC0xLnByb2Qud29ya3Nob3BzLmF3cy9hOTY5NmQyOC1lMDdlLTQxZjItYjFhYy1hZTQwZmFmNDZlYzAvKiIsIkNvbmRpdGlvbiI6eyJEYXRlTGVzc1RoYW4iOnsiQVdTOkVwb2NoVGltZSI6MTc5MTMwNDkxNH19fV19&Signature=s%7Ez91GYmw9jKzcfaM8PS%7EjoZJbP5pNH4MO%7EMxb8SOLh%7EWsyq4Yq5pLxbwr8-Lo8sToX-yB2YlRB99PKqwgSdEuJ33vedA59oGhwWdvCuK1i5stMLKRlGOcVgV9hJma4c-I1GQi%7EoPK9H4l8hXUqVhD4bVAbEHS86nmDvmAU5zZD1Davhx9TfdCmWg0zy0QrzRUNjOW3QeLYaaWNXf4wSH%7EIPpAIbC-2dfevrI4RT9quqQdUoA2s4%7EEu9z4mufpH0-1ZZiaKNz9GHqFsigaqpmUoWxequ%7EDEvhYS%7EAG7QTxvLrG9RV7fmqPQAhhsPAO4%7EZX4gOkDu00Te3kt7q%7Ea6fQ__)

One Shared Provider

| Pros | Cons |
| --- | --- |
| Best resource utilization | No isolation between functions |
| Lowest baseline cost (one three-instance floor for all) | Noisy-neighbor risk between workloads |
| Simplest to manage and monitor | Same scaling policy applies to every function |

Use this when all functions belong to the same team, share the same trust level, and have similar performance profiles.

## Strategy 2: One provider per tenant

Each tenant or trust level gets its own capacity provider.

![One Provider Per Tenant](https://static.us-east-1.prod.workshops.aws/a9696d28-e07e-41f2-b1ac-ae40faf46ec0/static/images/module-4/architecture-1-provider-per-tenant.png?Key-Pair-Id=K36Q2WVO3JP7QD&Policy=eyJTdGF0ZW1lbnQiOlt7IlJlc291cmNlIjoiaHR0cHM6Ly9zdGF0aWMudXMtZWFzdC0xLnByb2Qud29ya3Nob3BzLmF3cy9hOTY5NmQyOC1lMDdlLTQxZjItYjFhYy1hZTQwZmFmNDZlYzAvKiIsIkNvbmRpdGlvbiI6eyJEYXRlTGVzc1RoYW4iOnsiQVdTOkVwb2NoVGltZSI6MTc5MTMwNDkxNH19fV19&Signature=s%7Ez91GYmw9jKzcfaM8PS%7EjoZJbP5pNH4MO%7EMxb8SOLh%7EWsyq4Yq5pLxbwr8-Lo8sToX-yB2YlRB99PKqwgSdEuJ33vedA59oGhwWdvCuK1i5stMLKRlGOcVgV9hJma4c-I1GQi%7EoPK9H4l8hXUqVhD4bVAbEHS86nmDvmAU5zZD1Davhx9TfdCmWg0zy0QrzRUNjOW3QeLYaaWNXf4wSH%7EIPpAIbC-2dfevrI4RT9quqQdUoA2s4%7EEu9z4mufpH0-1ZZiaKNz9GHqFsigaqpmUoWxequ%7EDEvhYS%7EAG7QTxvLrG9RV7fmqPQAhhsPAO4%7EZX4gOkDu00Te3kt7q%7Ea6fQ__)

One Provider Per Tenant

| Pros | Cons |
| --- | --- |
| Strong isolation between tenants | Higher baseline cost (three instances per provider) |
| Independent scaling policy per tenant | More providers to manage |
| No cross-tenant noisy-neighbor risk | Lower utilization per provider |

Use this when tenants are not mutually trusted, have different SLAs, or face regulatory requirements that demand separation.

## Strategy 3: One provider per trust tier

Group functions by trust level, not individual tenant.

![One Provider Per Trust Tier](https://static.us-east-1.prod.workshops.aws/a9696d28-e07e-41f2-b1ac-ae40faf46ec0/static/images/module-4/architecture-1-provider-per-trust.png?Key-Pair-Id=K36Q2WVO3JP7QD&Policy=eyJTdGF0ZW1lbnQiOlt7IlJlc291cmNlIjoiaHR0cHM6Ly9zdGF0aWMudXMtZWFzdC0xLnByb2Qud29ya3Nob3BzLmF3cy9hOTY5NmQyOC1lMDdlLTQxZjItYjFhYy1hZTQwZmFmNDZlYzAvKiIsIkNvbmRpdGlvbiI6eyJEYXRlTGVzc1RoYW4iOnsiQVdTOkVwb2NoVGltZSI6MTc5MTMwNDkxNH19fV19&Signature=s%7Ez91GYmw9jKzcfaM8PS%7EjoZJbP5pNH4MO%7EMxb8SOLh%7EWsyq4Yq5pLxbwr8-Lo8sToX-yB2YlRB99PKqwgSdEuJ33vedA59oGhwWdvCuK1i5stMLKRlGOcVgV9hJma4c-I1GQi%7EoPK9H4l8hXUqVhD4bVAbEHS86nmDvmAU5zZD1Davhx9TfdCmWg0zy0QrzRUNjOW3QeLYaaWNXf4wSH%7EIPpAIbC-2dfevrI4RT9quqQdUoA2s4%7EEu9z4mufpH0-1ZZiaKNz9GHqFsigaqpmUoWxequ%7EDEvhYS%7EAG7QTxvLrG9RV7fmqPQAhhsPAO4%7EZX4gOkDu00Te3kt7q%7Ea6fQ__)

One Provider Per Trust Tier

| Pros | Cons |
| --- | --- |
| Balances cost against isolation | Requires clear trust-level definitions |
| Production shielded from dev/staging workloads | Functions within a tier still share resources |
| Manageable number of providers | Governance needed to enforce correct placement |

Use this when your organization has clear environment boundaries (prod/staging/dev) or trust tiers (internal/external, PCI/non-PCI).

## Choosing a strategy

Work through the questions in order. The first "yes" that requires isolation ends the process:

| Question | If yes | If no |
| --- | --- | --- |
| Do tenants have separate compliance or regulatory boundaries? | One provider per tenant | Continue |
| Could one function's failure or excessive load hurt another? | Isolate them by team or tier | Continue |
| Do workloads need different scaling policies? | Separate providers per policy | Continue |
| Do all functions belong to the same team, same trust level? | Shared provider is fine | Reconsider tier-based isolation |

## Capacity provider quotas

Two quotas affect your grouping decision:

| Quota | Limit | Impact |
| --- | --- | --- |
| Capacity providers per account | 1,000 | Not typically a constraint, even with per-tenant isolation |
| Function versions per capacity provider | 100 (hard limit, cannot be increased) | Limits how many function versions can share a single provider. If you have many microservices, each with frequent deploys, you may hit this on a shared provider |

The function version limit matters most for the "one shared provider" strategy. Each published version counts against the limit, including old versions you have not cleaned up. If your team publishes frequently and does not prune old versions, a shared provider fills up faster than isolated ones.

Lambda counts every published function version attached to a capacity provider. Delete unused versions to stay within the 100-version limit. Check the **Function versions** tab on your capacity provider in the Lambda console to see current usage.

## Service-linked role

Lambda uses the `AWSServiceRoleForLambda` service-linked role to manage the EC2 instances in your capacity providers. This role is created automatically the first time you create a capacity provider. You do not need to create it manually, but your account must allow service-linked role creation (some organizations restrict this via SCPs).

If capacity provider creation fails with a permissions error and your operator role looks correct, check whether your organization's SCPs allow `iam:CreateServiceLinkedRole` for the `lambda.amazonaws.com` service.

## Enforcing placement with IAM

The `lambda:PassCapacityProvider` action gates which users or roles can attach functions to which capacity providers. Combined with a naming convention, it becomes the mechanism you use to enforce your grouping policy.

The following policy lets its holder attach functions only to capacity providers whose names start with `production-`. Replace `123456789012` with your account ID (`echo $ACCOUNT_ID`):

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": "lambda:PassCapacityProvider",
      "Resource": "arn:aws:lambda:*:123456789012:capacity-provider:production-*"
    }
  ]
}
```

A developer with this policy cannot attach a function to a `tenant-b-*` provider or to any provider outside the `production-*` set. Applied consistently across teams, this turns your capacity-provider naming convention (`production-payments`, `dev-shared`, `tenant-b-workloads`) into an enforceable governance boundary.

This action is required when creating LMI functions, updating a function to use a different capacity provider, and deploying LMI functions through infrastructure-as-code pipelines. Grant it deliberately.

With the grouping model chosen and the IAM guardrail in place, deploy a second capacity provider and see the isolation in action.
