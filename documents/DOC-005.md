You will intentionally trigger throttling by sending more concurrent requests than your function can handle, even though CPU utilization remains low. Then you will observe the capacity provider scaling out new instances in response.

Sample outputs below were captured during workshop testing. Your throttle counts, instance counts, and metric values will differ based on timing, region, and current scaling state. The key patterns (throttling at low CPU, scale-out over successive waves) should be consistent.

With standard Lambda, throttling occurs when you hit account-level concurrency limits. With LMI, throttling happens when **all execution environments reach their configured max concurrency**, regardless of CPU utilization.

Your current configuration from Module 1:

- **3 execution environments** (minimum default)
- **16 concurrent requests per vCPU** (Python default)
- **1 vCPU per environment** (2 GB memory with 2:1 ratio)

This gives you capacity for **48 concurrent requests**. To trigger throttling, you need to send more than 48 concurrent requests.

## Phase 1: Trigger throttling

Use the `lmi-workshop-load-test` function to send 60 concurrent requests to `lmi-workshop-function:1` from Module 1 (exceeding the 48-slot capacity). If you used a different version number, update the `target_function` parameter below:

```bash
echo "=== Phase 1: Sending 60 concurrent requests (capacity is 48) ==="
aws lambda invoke --function-name lmi-workshop-load-test \
  --payload '{"target_function": "lmi-workshop-function:'$LMI_VERSION'", "concurrency": 60, "payload": {"count": 500000}}' \
  --cli-binary-format raw-in-base64-out ./throttle-test.json

cat ./throttle-test.json | python3 -m json.tool
```

You should see output like:

```json
{
    "statusCode": 200,
    "body": "{\"success\": 48, \"throttled\": 12, \"errors\": 0}"
}
```

Approximately 48 requests succeed and the rest get throttled. This confirms that concurrency saturation (not CPU) is the throttling trigger.

Your numbers may differ slightly. The exact split depends on timing and how quickly requests complete. The key observation is that some requests are throttled even though CPU is not maxed out.

## Phase 2: Sustained load to trigger further scaling

Now send higher concurrency (250 requests) to push beyond the newly scaled capacity. Run this multiple times with a 30-second gap to observe the scaler responding:

```bash
echo "=== Phase 2: Sustained load with 250 concurrent requests ==="
echo "Pushing beyond the scaled capacity to observe continued scaling"
echo ""

for WAVE in $(seq 1 6); do
  echo "--- Wave $WAVE ($(date +%H:%M:%S)) ---"
  aws lambda invoke --function-name lmi-workshop-load-test \
    --payload '{"target_function": "lmi-workshop-function:'$LMI_VERSION'", "concurrency": 250, "payload": {"count": 500000}}' \
    --cli-binary-format raw-in-base64-out ./wave-$WAVE.json > /dev/null 2>&1
  cat ./wave-$WAVE.json | python3 -c "import json,sys; d=json.load(sys.stdin); body=json.loads(d['body']); print(f'  Success: {body[\"success\"]}, Throttled: {body[\"throttled\"]}')"
  if [ $WAVE -lt 6 ]; then
    echo "  Waiting 30 seconds..."
    sleep 30
  fi
done

echo ""
echo "=== Phase 2 complete ==="
```

Over the 2.5 minutes, you should observe the throttle count decreasing as the capacity provider scales:

- **Wave 1:** Some requests throttled as scaling begins (250 exceeds current capacity)
- **Later waves:** Fewer throttled as new instances and environments come online

```
--- Wave 1 ---
  Success: 244, Throttled: 6
--- Wave 2 ---
  Success: 250, Throttled: 0
--- Wave 3 ---
  Success: 250, Throttled: 0
...
--- Wave 6 ---
  Success: 250, Throttled: 0
```

Wave 1 still shows some throttling as the scaler provisions new capacity. By Wave 2, the system has scaled to handle 250 concurrent requests without any throttles. The scaling response is fast once triggered.

The scaling response depends on how much headroom remains under your `MaxVCpuCount: 30` limit. If throttling persists even in later waves, you have hit the vCPU cap. The next step (Configure Scaling) shows how to adjust this.

## Observe scaling in action

Check how many instances are now running:

```bash
echo "Instances in capacity provider:"
aws ec2 describe-instances \
  --include-managed-resources \
  --filters "Name=tag:aws:lambda:capacity-provider,Values=*lmi-workshop-capacity-provider" \
            "Name=instance-state-name,Values=running" \
  --query "Reservations[*].Instances[*].[InstanceId,InstanceType,LaunchTime]" \
  --output table
```

You should see more than the original 3 instances. The capacity provider scaled out to handle the sustained load:

  --namespace AWS/Lambda \
  --metric-name ExecutionEnvironmentConcurrency \
  --dimensions Name=CapacityProviderName,Value=lmi-workshop-capacity-provider \
               Name=FunctionName,Value=lmi-workshop-function \
               Name=Resource,Value=lmi-workshop-function:$LMI_VERSION \

## The key insight

**LMI does not scale like standard Lambda.** Standard Lambda scales by launching new execution environments when invocations arrive. LMI scales by monitoring resource consumption and concurrency saturation across existing environments, then provisioning additional instances asynchronously.

This means:

- Throttling happens when concurrency is saturated, **not when CPU is high**
- Scaling is **asynchronous**. It takes 1-2 minutes for new instances to come online
- Once scaled, the additional capacity handles subsequent waves without throttling

In the next step, you will configure scaling parameters to handle higher throughput without throttling.
